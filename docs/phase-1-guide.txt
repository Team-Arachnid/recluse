For someone who has not worked on this project before.
================================================================================

Read this whole file once before you type anything. It is long because the
mistakes in this phase are silent -- they do not crash, they just quietly make

--------------------------------------------------------------------------------
0. FIRST, A CORRECTION ABOUT NAMING
--------------------------------------------------------------------------------

Phase 1 does NOT train a model. Nothing here calls .fit() on a classifier.

  Phase 1 (you are here)  Turn raw CSVs into clean, correctly split,
                          correctly scaled data + a saved preprocessing bundle.

  Phase 2                 Train Model A, the supervised classifier
                          (RandomForest, then LightGBM). Produces
                          supervised_model.pkl.

  Phase 3                 Train Model B, the autoencoder, on benign traffic
                          only. Produces autoencoder.pt.

Phase 2 cannot start until Phase 1 is finished, because there is nothing to
train on until you produce the splits. If you get Phase 1 wrong, Phase 2 and
Phase 3 will produce impressive numbers that mean nothing. That is the whole
reason this phase is separate and has its own checkpoint.

What you deliver at the end of Phase 1:

  data/interim/*.parquet              cleaned data, one file per source day
  data/processed/train.parquet        temporal split
  data/processed/val.parquet
  data/processed/test.parquet
  data/processed/benign_train.parquet benign-only, for Phase 3
  backend/artifacts/preprocessing.pkl scaler + feature order + schema hash
  A printed table of row counts per split per class
  A short written note on every cleaning decision you made


--------------------------------------------------------------------------------
1. BACKGROUND: WHAT THE PROJECT IS
--------------------------------------------------------------------------------

Recluse detects network attacks using two models working together.

  Stage 1  A supervised classifier. It has seen labelled examples of specific
           attacks (DoS, port scan, brute force...) and it names them.
           Weakness: it can only recognise what it was trained on.

  Stage 2  An autoencoder trained ONLY on normal (benign) traffic. It learns
           what normal looks like and reports how badly a flow fails to fit
           that picture. It has never seen a single attack label.
           Strength: it can flag attacks nobody ever labelled for it.

The claim the project has to defend is that it catches attack traffic it was
never trained on. Stage 2 is what makes that claim, and Stage 2 only works if
its training data is genuinely 100% benign. Guarding that is partly your job
in this phase.

Vocabulary you will need immediately:

  flow        One network conversation, summarised as ~78 numbers (duration,
              packet counts, byte rates, inter-arrival times...). You are not
              working with raw packets. One row of the CSV = one flow.
  benign      Normal, non-attack traffic.
  label       The column saying what a flow was: BENIGN, DoS Hulk, PortScan...
  leakage     When a column lets the model identify the answer through a
              shortcut instead of learning attack behaviour. Poison.
  split       Dividing data into train / validation / test so you can measure
              honestly on data the model never saw.

3. STEP 1 - GET THE DATASET
--------------------------------------------------------------------------------

Dataset: CICIDS2017, from the Canadian Institute for Cybersecurity (UNB).

  https://www.unb.ca/cic/datasets/ids-2017.html

Download the pre-extracted flow features, usually distributed as
MachineLearningCSV.zip. You want the CSVs, NOT the raw pcap files. The pcaps
are hundreds of gigabytes and you do not need them in this phase.

Expect roughly 8 CSV files and on the order of 2.8 million rows in total.
Treat every number in this guide as approximate and verify against what you
actually download.

Unzip into data/raw/. The files as distributed are named roughly like this:

  Monday-WorkingHours.pcap_ISCX.csv
  Tuesday-WorkingHours.pcap_ISCX.csv
  Wednesday-workingHours.pcap_ISCX.csv
  Thursday-WorkingHours-Morning-WebAttacks.pcap_ISCX.csv
  Thursday-WorkingHours-Afternoon-Infilteration.pcap_ISCX.csv
  Friday-WorkingHours-Morning.pcap_ISCX.csv
  Friday-WorkingHours-Afternoon-PortScan.pcap_ISCX.csv
  Friday-WorkingHours-Afternoon-DDos.pcap_ISCX.csv

Two warnings about these names:

  - "Infilteration" is misspelled in the actual dataset. That is not a typo in
    this guide. Do not silently "fix" it in your code and then wonder why the
    file is not found. Match the real filenames on disk.
  - Capitalisation is inconsistent ("WorkingHours" vs "workingHours"). On
    Linux that matters. Use a glob and log what you matched rather than
    hardcoding a list of eight strings.

Write your loader to list what it found and fail loudly with a clear message
if a day is missing. Half a dataset produces half a result and no error.

ONE MORE THING, AND IT IS IMPORTANT:
The original CICIDS2017 labels contain documented errors, and corrected
re-releases exist. You are not expected to fix them. You ARE expected to know
it and say so. Put a line in the README noting it. Reviewers know this about
the dataset, and acknowledging it signals you read past the abstract.

Also: do not swap in NSL-KDD as the primary dataset. It derives from 1999
traffic and reviewers will discount the whole result.

4. STEP 2 - LOOK AT THE DATA BEFORE YOU WRITE ANY CODE
--------------------------------------------------------------------------------

Spend twenty minutes here. It will save you a day.

  cd backend

Then, interactively:

  import pandas as pd
  df = pd.read_csv("../data/raw/Monday-WorkingHours.pcap_ISCX.csv", nrows=5000)
  print(df.shape)

    " Flow Duration" is not "Flow Duration". df[" Flow Duration"] works and
    df["Flow Duration"] raises KeyError. This single detail breaks more
    attempts at this dataset than anything else.
  - The label column is called " Label" (with a leading space).
  - There is a duplicated column, "Fwd Header Length" appearing twice, the
    second usually as "Fwd Header Length.1".
  - Look at "Flow Bytes/s". You will find inf and NaN values.
  - Check df[" Label"].value_counts() on a full day file. Notice how
    overwhelmingly BENIGN dominates. That imbalance is why accuracy is a
    useless metric on this project.

5. STEP 3 - WRITE clean.py
--------------------------------------------------------------------------------

Fill in backend/training/clean.py. Its docstring already lists the six known
defects. Handle each one explicitly and LOG what you did -- you need those
numbers for your write-up at the end.

Suggested shape:

  def main() -> None:
      for csv_path in discover_raw_files():
          frame = pd.read_csv(csv_path, low_memory=False)
          frame = normalise_headers(frame)
          frame = fix_infinities(frame)
          frame = drop_duplicate_rows(frame)
          frame = drop_zero_variance_columns(frame)
          frame = fix_negative_values(frame)
          frame = normalise_labels(frame)
          write_parquet(frame, interim_path_for(csv_path))
      print_summary()

5.1 HEADERS - strip and snake_case, first, before anything else.

    Use the function that already exists. Do not write your own:

      from training.features import normalise_columns
      frame.columns = normalise_columns(list(frame.columns))

    " Flow Duration" becomes "flow_duration". "Flow Bytes/s" becomes
    "flow_bytes_s". "Fwd Header Length.1" becomes "fwd_header_length_1".

    Why it must be first: every later step refers to columns by name. Do this
    once, centrally, and every subsequent line of code becomes reliable.

    Why use the shared function: serving code must normalise names identically
    to training code. If you write a second version here, the two will drift
    and the API will silently feed the model the wrong columns.

5.2 INFINITIES - flow_bytes_s and flow_packets_s contain inf and NaN.

    Cause: these are rates, bytes divided by duration. Flows with zero
    duration divide by zero.

      frame = frame.replace([np.inf, -np.inf], np.nan)

    Then decide: drop those rows, or fill them. Either is defensible.
    Dropping is simpler and the count is small. Filling with zero is arguably
    more truthful (a zero-duration flow did not transfer at infinite speed).

    WHICHEVER YOU CHOOSE, WRITE DOWN WHICH AND WHY, AND LOG THE COUNT.
    "We dropped 1,432 rows with non-finite rate values, 0.05% of the data"
    is a sentence that belongs in your notes. An unexplained choice here is
    the kind of thing that gets asked about.

5.3 DUPLICATE ROWS - this is the big one.

      before = len(frame)
      frame = frame.drop_duplicates()
      print(f"dropped {before - len(frame)} exact duplicate rows")

    Read this paragraph twice. This dataset contains a very large number of
    exactly identical rows. If you do not remove them BEFORE splitting, the
    same row ends up in both your training set and your test set. The model
    then gets tested on rows it memorised, and you will see 99.9% scores.

    Those scores are fake. This is the single largest source of inflated
    results in published work using this dataset. A reviewer who sees 99.9%
    assumes this bug immediately, so the high score actively damages you.

    Expect to lose a substantial fraction of the data. That is correct and
    good. Log the exact count.

5.4 ZERO-VARIANCE COLUMNS - columns that are the same value in every row.

    bwd_psh_flags, fwd_urg_flags and several others are all-zero throughout.
    A column with one distinct value carries no information; it just adds
    noise and training time.

    Find them programmatically, do not hardcode a list:

      constant = [c for c in numeric_cols if frame[c].nunique(dropna=False) <= 1]

    Log exactly which columns you dropped. You will need that list for the
    dropped_columns entry in the preprocessing bundle in step 7.

    CAUTION: compute this on the TRAINING data, not on each file separately.
    A column can be constant on Monday and informative on Friday. Simplest
    safe approach: clean each day, concatenate, then compute zero-variance on
    the training split only, and apply that same list everywhere.

5.5 NEGATIVE VALUES - some duration and IAT columns contain them.

    A duration cannot be negative; these are artefacts. Clip at zero or drop
    the rows. Log the count either way.

      (IAT means inter-arrival time: the gap between consecutive packets.)

5.6 LABELS - collapse to the project's eight classes.

    The raw labels are specific (DoS Hulk, DoS GoldenEye, DoS slowloris, ...).
    The project uses eight classes. The exact list lives in
    backend/app/models.py as ALERT_FAMILIES, plus benign:

      benign, dos, ddos, brute_force, port_scan, web_attack, botnet,
      infiltration

    So for example:
      BENIGN                                          -> benign
      DoS Hulk / GoldenEye / slowloris / Slowhttptest -> dos
      DDoS                                            -> ddos
      FTP-Patator / SSH-Patator                       -> brute_force
      PortScan                                        -> port_scan
      Web Attack - Brute Force / XSS / Sql Injection  -> web_attack
      Bot                                             -> botnet
      Infiltration                                    -> infiltration
      Heartbleed                                      -> decide and document

    Write the mapping as an explicit dictionary in code, and LOG IT. Also log
    any raw label that did not match your mapping -- do not let an unmapped
    label silently become NaN or get dropped. Assert that every row got a
    class.

    Note the raw web attack labels sometimes contain odd characters or
    inconsistent dashes. Check the actual distinct values rather than assuming.

5.7 WRITE PARQUET, NOT CSV.

      frame.to_parquet(out_path, index=False)

    Two reasons: it reloads about ten times faster, and it preserves dtypes.
    CSV turns everything back into strings and you re-guess types every run.
    (pyarrow is already installed.)

Verify step 3 before moving on:

  - Reload a written Parquet file and confirm no inf and no NaN survive:
      assert np.isfinite(frame.select_dtypes("number")).all().all()
  - Confirm frame.duplicated().sum() == 0
  - Confirm every row has a class from the eight

6. STEP 4 - WRITE split.py (THE PART THAT IS EASY TO GET WRONG)
--------------------------------------------------------------------------------

THE RULE: TEMPORAL SPLITS ONLY.

Never, under any circumstances, write this:

      train_test_split(X, y, shuffle=True)     # DO NOT DO THIS

Why: flow records are heavily duplicated and strongly correlated in time.
Random splitting scatters near-identical rows across train and test, so the
model is tested on what it effectively memorised. It manufactures fake scores.
This is listed as an anti-pattern in BUILD_PROMPT.md PART 12.

Instead, split by DAY. The dataset is designed for this:

  Monday      benign only                              -> autoencoder train
  Tuesday     FTP-Patator, SSH-Patator                 -> train
  Wednesday   DoS Hulk/GoldenEye/Slowloris/
              Slowhttptest, Heartbleed                 -> train
  Thursday    web attacks (AM), infiltration (PM)      -> validation
  Friday      botnet, port scan, DDoS                  -> test

This is better than a random split for a real reason, not just a safer one:
the model trains on earlier traffic and is tested on later traffic, which is
how it would actually be deployed.

Monday being benign-only is a gift. It is a clean autoencoder training set
with zero label contamination. Write it out separately as
data/processed/benign_train.parquet.

FOR PHASE 3, WHICH DEPENDS ON YOU:
The autoencoder training set must be benign rows ONLY -- Monday in full, plus
the benign rows from Tuesday and Wednesday. Not one attack row. Assert it in
code, do not just intend it:

      assert (benign_train["label"] == "benign").all(), "attack rows leaked in"

If an attack row gets into that file, Stage 2 quietly stops being a
novel-attack detector and becomes a weak supervised model, and the project's
main claim collapses. This assert is the cheapest insurance in the codebase.


--------------------------------------------------------------------------------
7. STEP 5 - DROP THE LEAKAGE COLUMNS
--------------------------------------------------------------------------------

Drop the identity columns before training:

      flow_id, source_ip, destination_ip, source_port

They are already listed in features.py as LEAKAGE_COLUMNS. Import that tuple
rather than retyping it. Note it actually holds seven entries, because it also
covers the short-form spellings (src_ip, dst_ip, src_port) that appear in some
re-releases and in CICFlowMeter output. Matching both spellings means the same
deny-list works whichever source the data came from.

Why: in this lab capture, the attacker always ran from the same machine. If
you leave the source IP in, the model learns "traffic from 172.16.0.1 is an
attack". That scores beautifully on this dataset and is completely useless on
any real network. It has learned the lab's addressing scheme, not attack
behaviour.

TIMESTAMP is a special case. You NEED it to build the temporal split, so keep
it through split.py, then drop it before training. features.py marks this as
SPLIT_ONLY_COLUMNS. If timestamp reaches the model it learns "attacks happen
on Wednesday afternoon", which is the same failure in a different costume.


--------------------------------------------------------------------------------
8. STEP 6 - THE DESTINATION PORT DECISION
--------------------------------------------------------------------------------

destination_port is deliberately NOT in the leakage list. It needs a decision
from you, not a default.

The tension: the port is genuinely informative (port 80 is web traffic, port
22 is SSH, and attacks do target specific services). It is also a memorisation
trap, because in a lab capture the attacks were aimed at a small fixed set of
ports.

What the spec asks you to do: prepare BOTH encodings, so Phase 2 can train
twice and compare.

  Encoding A - raw:      keep destination_port as an integer feature.

  Encoding B - bucketed: map the port into service groups
                           well-known    0-1023
                           registered    1024-49151
                           ephemeral     49152-65535
                         plus a one-hot column for each of the top 20 most
                         frequent ports in the TRAINING data only.

Record which encoding a bundle used in the port_encoding field, so the choice
is never ambiguous later:

      port_encoding = {"strategy": "raw"}
      port_encoding = {"strategy": "buckets", "top_ports": [80, 443, ...]}

Then, in Phase 2, if raw port produces a large accuracy gain over bucketed,
treat that gain as suspicious and say so in writing. A large gain means the
model is memorising the lab's port assignments rather than learning attack
behaviour. Reporting that honestly is worth more than the higher number.

Compute the top-20 port list from TRAINING data only. Deriving it from the
full dataset leaks test-set information into your features.

9. STEP 7 - SCALING AND THE ARTIFACT BUNDLE
--------------------------------------------------------------------------------

9.1 Use RobustScaler. Not StandardScaler.

      from sklearn.preprocessing import RobustScaler
      scaler = RobustScaler()
      scaler.fit(X_train)          # TRAIN ONLY. Never fit on val or test.

    Why: network flow features are extremely heavy-tailed. A handful of
    enormous flows (one huge file transfer) dominate the mean and standard
    deviation, and StandardScaler squashes every normal value into a narrow
    band near zero. RobustScaler uses the median and interquartile range, so
    a few giant flows cannot flatten everything else.

    Why fit on train only: fitting on all the data lets test-set statistics
    influence your transform. That is leakage, subtler than an IP column but
    the same category of error. Fit on train, then TRANSFORM val and test with
    that already-fitted scaler.

9.2 Save the bundle. Helpers already exist -- use them:

      from training.features import (
          build_preprocessing_bundle,
          save_preprocessing_bundle,
      )

      bundle = build_preprocessing_bundle(
          scaler=scaler,
          feature_order=list(X_train.columns),   # EXACT column order
          dropped_columns=dropped,               # from steps 5.4 and 7
          port_encoding=port_encoding,           # from step 6
      )
      save_preprocessing_bundle(
          bundle, settings.artifacts_path / "preprocessing.pkl"
      )

    build_preprocessing_bundle computes the schema_hash for you -- a SHA-256
    of the exact feature order.

    WHY THE HASH MATTERS, because this is the most important paragraph in the
    guide: if the API ever feeds the model columns in a DIFFERENT ORDER than
    training used, every score becomes garbage and NOTHING RAISES AN
    EXCEPTION. The model happily accepts the numbers and returns confident
    nonsense. This is called train/serve skew and it is the silent killer of
    projects like this.

    The hash converts that silent failure into a refused startup. The backend
    recomputes it at boot and will not serve on a mismatch. That check already
    works -- there is a test for it in
    backend/tests/test_api_surface.py. Your job is simply to produce a bundle
    with a correct, matching hash.

    So: scaler, feature order and hash travel together, in one file. Any one
    of them alone is not enough to reproduce the training feature matrix.

9.3 Implement build_feature_matrix in features.py.

    It currently raises NotImplementedError. This is the function BOTH training
    and the live API call, and that is the entire point: one implementation,
    so the two paths cannot diverge.

      def build_feature_matrix(frame, bundle=None):
          # drop leakage columns
          # apply the port encoding
          # reindex to bundle["feature_order"]     <- order matters
          # apply bundle["scaler"].transform(...)
          # return the matrix

    When bundle is None you are in training and fitting. When bundle is
    provided you are applying a saved transform.

    DO NOT reimplement any of this inside backend/app/. If you find yourself
    writing a transform in the API, stop -- that is the skew bug being born.

10.5 preprocessing.pkl exists, and the backend still starts. Run:

      cd backend
      uv run uvicorn app.main:app

    Watch the startup log. You should see a line reading
    "schema hash verified: sha256:... (N features)". If instead the process
    refuses to start with a SchemaHashMismatch, your bundle is internally
    inconsistent -- rebuild it, do not work around the check.

10.6 Your written decisions. Short, specific, one line each:

      - rows dropped for non-finite rates, and why drop vs impute
      - exact duplicate rows dropped
      - zero-variance columns dropped (the list)
      - negative values clipped or dropped, and the count
      - the label collapsing map
      - which port encodings you produced
      - the final feature count

10.7 Run the existing tests to confirm you broke nothing:

    All tests should pass. If you changed features.py, the tests in

--------------------------------------------------------------------------------
11. MISTAKES THAT WILL COST YOU THE PROJECT
--------------------------------------------------------------------------------

Ranked by how much damage they do and how easy they are to make.

1.  train_test_split(shuffle=True). Fake 99.9% scores. Use day-based splits.

2.  Not dropping duplicate rows before splitting. Same outcome, and it is
    invisible unless you check for it.

3.  Any attack row in the autoencoder training set. Destroys the project's
    central claim. Assert against it.

4.  Fitting the scaler on all the data instead of train only. Leakage.

5.  Reimplementing a transform inside backend/app/ instead of using
    features.py. Silent train/serve skew. No exception, wrong answers forever.

6.  Leaving source_ip or timestamp in the feature set. The model learns the
    lab, not the attack.

7.  Computing the top-20 port list, or the zero-variance list, from the full
    dataset instead of from train only.

8.  Using SMOTE. Do not. Synthetic interpolation between two flow records
    invents packets that could not exist on a real network, and applying it
    before the split puts synthetic rows into your test set. If you want to
    demonstrate it, do it as an ablation in Phase 2 and show it underperforms.

9.  Reporting accuracy as your headline. The data is about 99% benign, so
    always answering "benign" scores 99%. It tells you nothing.

10. Being quiet about a decision. Every choice you make in this phase needs a
    one-line justification. An unexplained choice reads as an accident.

11. Committing the dataset. data/ is gitignored for a reason -- it is several
    gigabytes and it is redistributable from the source.


--------------------------------------------------------------------------------
12. IF YOU GET STUCK
--------------------------------------------------------------------------------

  KeyError on a column name
      You did not normalise the headers, or you normalised twice. Print
      list(frame.columns) and look at what you actually have.

  "Only one class present in y" or similar
      You are looking at one day in isolation. Monday is benign-only, so this
      is expected there.

  Memory errors loading everything at once
      Clean day by day, write each to Parquet, then concatenate. Or pass
      dtype= to read_csv to avoid float64 for everything.

  SchemaHashMismatch when starting the backend
      The feature_order in your bundle does not hash to the stored
      schema_hash. You probably built the bundle by hand. Use
      build_preprocessing_bundle, which computes it for you.

  Backend will not start at all, unrelated to the bundle
      Confirm .env exists (.\make.ps1 env creates it) and migrations are
      applied (.\make.ps1 migrate).

  Something in this guide contradicts BUILD_PROMPT.md
      BUILD_PROMPT.md wins. Flag the contradiction so this file gets fixed.
